# Security Implementation Guide

## Core Configuration

### Required Environment Variables

All three secrets are mandatory. The server exits before listening if any is missing, shorter than
32 characters, or contains placeholder text. Nothing is auto-generated by the application.

```bash
JWT_SECRET=<min 32 chars, required>
REFRESH_TOKEN_SECRET=<min 32 chars, required>
SESSION_SECRET=<min 32 chars, required>
```

**Generate three separate values:**
```bash
openssl rand -base64 52   # use as JWT_SECRET
openssl rand -base64 52   # use as REFRESH_TOKEN_SECRET
openssl rand -base64 52   # use as SESSION_SECRET
```

### Secret Validation

- `startup-validation.js` runs in the Docker entrypoint and rejects missing, short, placeholder,
  weak-substring, and low-diversity values for all three secrets.
- `server/middleware.ts` and `server.ts` also validate presence, minimum length (32), and
  placeholder text at module load/startup; failures exit with code 1.
- Shannon entropy below 128 bits only logs a warning in `server/middleware.ts`; it does not block
  startup. Do not treat the "entropy check passed" log as a strict guarantee.

## Authentication Layers

### Layer 1: Session Cookies (express-session)

- Stored in the **main** SQLite database (`data/vault.db`, `/data/vault.db`, or `DB_PATH`) in an
  `express_session` table — there is no separate `sessions.db`.
- Cookie name: `connect.sid`.
- Session **cookie** lifetime: `SESSION_EXPIRY_MINUTES`, default `1440` minutes (24 hours). Stored
  `express_session` rows have no server-side TTL/sweeper and persist until logout or manual cleanup;
  rotating `SESSION_SECRET` makes existing cookies unusable.
- Cookie flags: `httpOnly`, `secure: 'auto'`, `sameSite: 'strict'`.
- Destroyed on logout via `req.session.destroy()`.

### Layer 2: JWT Bearer Tokens

- Access tokens: **1 hour** lifetime.
- Refresh tokens: **7 days**, with revocation via the `auth_tokens` table; rotation replaces the
  stored refresh token on every refresh.
- The resolver accepts `Authorization: Bearer`, `x-auth-token`, or query `token` / `auth`; refresh
  tokens are also accepted as bearer tokens. This provides a fallback for embedded/non-cookie contexts.
- Access JWTs are verified by signature plus a live user-existence/soft-delete DB check, but there is
  no token denylist, so they remain valid for up to 1 hour after a password change unless `JWT_SECRET`
  is rotated.

## Implemented Security Controls

### 1. Secret Enforcement ✅
- All three secrets are required with a 32-character minimum.
- Placeholder/example values are rejected; Docker additionally rejects common weak substrings and
  values with too little character variety.
- Low estimated entropy produces a warning, not a startup failure.

### 2. CSRF Protection ✅
- Double-submit pattern: the `x-csrf-token` header must match the `slag3d_csrf_token` cookie.
- The token is returned in login/refresh responses and set in a cookie; retrieve it with
  `GET /api/auth/csrf-token`.
- Required on unsafe (POST/PUT/DELETE/…) `/api` requests **except** `/api/auth/login`,
  `/api/auth/refresh`, `/api/auth/logout`, `/api/health`, and `/api/tags`.

### 3. Token Rotation ✅
- Refresh tokens are replaced on every refresh; logout deletes all refresh tokens for the user.
- API password change, admin password reset, and user soft-delete also delete `auth_tokens`.
- `npm run set-admin` changes the password hash directly and does **not** delete tokens or sessions.
- Existing sessions are not destroyed by password change/reset; logout destroys the stored row,
  while rotating `SESSION_SECRET` makes existing cookies unusable. There is no server-side session
  TTL/sweeper.

### 4. Rate Limiting ✅
- General API (admin, collections, models, tags): 200 requests/minute per IP.
- Uploads (`POST /api/models`, `POST /api/models/:id/files`): 30 requests/hour per IP.
- Login: 10 per 15 minutes; refresh: 10/hour; logout: 20/hour. `/api/health` is unthrottled.

### 5. Session & Token Invalidation ✅
- Logout destroys the session and deletes stored refresh tokens.
- Password change/reset deletes refresh tokens only; already-issued access JWTs and existing session
  rows remain valid until their own expiry or a corresponding secret rotation.

## Security Checklist

### Deployment Validation

```bash
# Check lengths in the current shell
echo "JWT: ${#JWT_SECRET} / Refresh: ${#REFRESH_TOKEN_SECRET} / Session: ${#SESSION_SECRET}"

# Docker runs this automatically. Locally, load .env into the environment first:
set -a; . ./.env; set +a
node startup-validation.js
```

Do not grep `.env` for "SECRET": every valid key contains that word, so the check proves nothing.

### Runtime Verification
- Startup log shows `[SLAG3D SECURITY] Security validation passed - JWT_SECRET, REFRESH_TOKEN_SECRET & SESSION_SECRET properly configured`.
- No `[SLAG3D CRITICAL ERROR]` or `[SLAG3D SECURITY ERROR]` messages.
- API endpoints respond correctly with valid tokens.

## Secrets Management Best Practices

### DO ✅
- Keep secrets in `.env` (never committed). Compose injects them as environment variables from that
  file; the application reads only `process.env`.
- Rotate secrets every 90 days and generate new values before deployment rotation.
- Terminate TLS at a reverse proxy and enforce HTTPS/HSTS there.

### DON'T ❌
- Commit `.env` files, hardcode secrets, share them unencrypted, or reuse them across services.
- Assume the Docker Swarm secrets example is wired in: it is illustrative only, and the app still
  reads all secrets from environment variables.

### Rotation Procedure

```bash
# 1. Generate three new secrets (see above), then REPLACE the existing values in .env.
#    Do not append duplicate keys — dotenv uses the last occurrence, which is fragile.

# 2. Restart the process with a command that actually stops the old one:
docker compose up -d --force-recreate  # Compose; restart does not re-read .env
systemctl restart slag3D.service       # LXC
# or stop the existing npm start / npm run dev process before starting it again
```

`npm restart` is **not** defined in this repo and does not stop a running server.

Effects of rotation:
- `SESSION_SECRET` change invalidates existing session cookies.
- `JWT_SECRET` change invalidates access JWTs.
- `REFRESH_TOKEN_SECRET` change invalidates stored refresh tokens.
- Rotate all three to revoke every token class.

## Startup Requirements

Missing/placeholder secrets are rejected at startup; there are no default JWT/session secrets. If an
older deployment used a weak secret, replace it and restart. Restarting alone does not revoke
sessions — only rotating `SESSION_SECRET` does.

The only default credential is the seeded admin password `admin123`, used only when seeding is
enabled (`GOOSE_SEED_DB=true`) and `ADMIN_PASSWORD` is not set while `users` is empty. Change it
immediately via the lock icon in the top navigation or `npm run set-admin -- 'NewStrongPassword'`.

## Security Headers (Actual Behavior)

There is no built-in HSTS, HTTPS, or referrer-policy environment configuration, and no Helmet
middleware. Implemented hardening is limited to:

- `X-Content-Type-Options: nosniff` on `/uploads` responses.
- `Content-Disposition: attachment` for stored model/PDF files under `/uploads/models`.
- Session cookies using `secure: 'auto'`, `httpOnly`, and `sameSite: 'strict'`.

Add global security headers and HSTS at the reverse proxy.

## Monitoring Recommendations

| Metric | Threshold | Action |
|--------|-----------|--------|
| Failed logins | App blocks at 10 attempts/15 min/IP | Alert on sustained failures |
| Session creation rate | Spike >200%/hour | Investigate anomalous user activity |
| Token validation errors | Elevated rate | Check clock sync, possible replay attacks |
| CSRF token failures | Any non-zero | Potential attack attempt |
