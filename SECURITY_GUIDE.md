# Security Implementation Guide

## Core Configuration

### Required Environment Variables

```bash
JWT_SECRET=<min 32 characters, secure random string>
SESSION_SECRET=<auto-generated or custom>
REFRESH_TOKEN_SECRET=<recommended for production>
```

**Generate secrets:**
```bash
openssl rand -base64 64 > secret.txt
echo "SECRET_KEY=$(cat secret.txt)"
```

### Secret Validation

On startup, the server validates:
- JWT_SECRET must be set and ≥32 characters
- Missing/weak secrets cause graceful shutdown (exit code 1)

## Authentication Layers

### Layer 1: Session Cookies (express-session)
- Stored in SQLite at `data/sessions.db`
- Cookie name: `connect.sid`
- Default expiry: 7 days (SESSION_EXPIRY_MINUTES)
- Destroyed on logout via `req.session.destroy()`

### Layer 2: JWT Bearer Tokens
- Access tokens: **1 hour** lifetime
- Refresh tokens: **7 days** with database revocation
- Fallback for iframe/sandbox environments
- Rotation enforced on every refresh

## Implemented Security Controls

### 1. Secret Enforcement ✅
- No fallback defaults for JWT_SECRET
- Minimum 32-character requirement enforced at runtime
- Server exits if secrets are missing/weak

### 2. CSRF Protection ✅
- Double-submit cookie pattern (`x-csrf-token` header)
- Token stored in response on login
- Required on state-changing endpoints
- `/api/csrf-token` endpoint for token retrieval

### 3. Token Rotation ✅
- Old refresh token deleted when new one issued
- All `auth_tokens` invalidated on password change
- Logout removes refresh token from database
- No reusable tokens after password change

### 4. Rate Limiting ✅
- Upload endpoint: 30 requests/hour per IP
- Collection endpoints: 50 requests/hour per IP
- Prevents DDoS via rapid uploads

### 5. Session Invalidation ✅
- Password change → all auth tokens deleted
- Logout → both session and refresh token invalidated
- Previous sessions immediately invalid after password reset

## Security Checklist

### Deployment Validation
```bash
# Verify JWT_SECRET is set
echo "Length: ${#JWT_SECRET}"  # Should be ≥32

# Confirm no placeholder values
grep -c 'EXAMPLE\|SECRET\|random' .env || echo "No placeholders found ✓"
```

### Runtime Verification
- Server logs show `[SLAG3D SECURITY] Security validation passed` on startup
- No `CRITICAL ERROR` messages in console output
- API endpoints respond correctly with valid tokens

## Secrets Management Best Practices

### DO ✅
- Store secrets in `.env` file (never committed to Git)
- Use Docker secrets for production
- Rotate secrets every 90 days
- Generate new secrets before deployment rotation

### DON'T ❌
- Commit `.env` files to version control
- Hardcode secrets in source code
- Share secrets via unencrypted channels
- Reuse the same secret across multiple services

### Rotation Procedure
```bash
# 1. Generate new secrets
openssl rand -base64 64 > jwt_new.txt
openssl rand -base64 64 > session_new.txt

# 2. Update .env file (backup old first)
cp .env .env.backup
echo "JWT_SECRET=$(cat jwt_new.txt)" >> .env
echo "SESSION_SECRET=$(cat session_new.txt)" >> .env

# 3. Restart server — old sessions will be invalidated automatically
npm restart

# 4. Instruct users to re-authenticate if needed
```

## Breaking Changes Notice

⚠️ **Deployments using default secrets MUST rotate:**

After applying these fixes:
1. Generate new secure secrets (min 32 characters)
2. Update `.env` file
3. Restart server immediately
4. Old cookies become invalid upon restart

If old weak secrets were in use, existing user sessions will be revoked on server restart. Plan rotation during maintenance window.

## Monitoring Recommendations

| Metric | Threshold | Action |
|--------|-----------|--------|
| Failed login attempts | >10/minute | Alert — possible brute force |
| Session creation rate | Spike >200%/hour | Investigate anomalous user activity |
| Token validation errors | Elevated rate | Check clock sync, possible replay attacks |
| CSRF token failures | Any non-zero | Potential attack attempt |
